The demo has no backend config at all. The real app has exactly one backend (the hosted database) and no browser-storage fallback. I worked only from the task text. The assumptions are listed under Decisions.\n\n**The gap in the task text:** it says the demo stores in the browser and the real app uses a hosted DB, but not what stops one from acting as the other. Two failure modes follow.\n- Public leak. The repo and the demo are public, so a backend URL or key in the demo bundle or the repo exposes the real data store.\n- Silent data loss. If the real app quietly falls back to browser storage when the DB is unreachable, a punch looks saved but lives on one phone. That is a P0 data-loss risk. The real app has to be single-backend and fail loudly.\n\n**Critical path** (each step is about one session)\n1. CRW-SEP-1 Build target switch (done when the AC below that are marked auto pass). The flag picks the storage adapter at build time, not at runtime. Dead code for the other adapter is excluded from the bundle.\n2. CRW-SEP-2 Config isolation. The real backend address and keys come only from the real app host's environment. Nothing in the repo or in the demo build env.\n3. CRW-SEP-3 Visible mode. The demo build artifact is scanned for the backend host and key patterns, and the build fails on a hit. The real build fails if the backend config is missing.\n5. CRW-SEP-5 Release check.
