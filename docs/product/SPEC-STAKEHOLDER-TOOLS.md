# SPEC: stakeholder tools, repo-check, claim-check, stakeholder-intake (SKT)

Step 2 of `docs/stakeholder-agent-plan.md`, after the package and checker (`docs/product/SPEC-STAKEHOLDER-PKG.md`, SKP). Scoped by staff-pm, Nov 24. Spec only; no tests or code yet. Three PRs, one tool each, in this order: `repo-check`, `claim-check`, `stakeholder-intake`.

## Answer
Build three small deterministic tools in `plugins/stakeholder/tools/`, each plain Node, no packages, no network, no model, each writing a JSON result the agent and `check-stakeholder` read. Goal fit: the agent's whole value is that every finding quotes text that exists (plan, "The loop"); today the agent has to build the quote index by hand (`stakeholder.md` step 2) and has no way to catch the overclaim that cost Chase most ("8 agents" when none were real), or to audit a repo's basics. Call: **build** all three (nothing existing does this), **reuse** `docs/repo-standards.md` by loading it and citing item ids (the checklist is the sibling thread's; nothing is copied), **reuse** `check-stakeholder`'s id rule and 1 MB cap, **skip** URL fetching and screenshots (`ux-shots`), per Chase.

## Bet, signal, stop
- **Bet:** Chase's readers never meet an invented quote or an unsupported number from this agent, and a stranger can run the three tools on their own repo, page or README without the studio. Signal: each tool's output passes through `check-stakeholder` unchanged on fixtures; on the first real runs (M2.4) every repo-check finding is accepted by Chase as true, and claim-check flags the planted "8 agents" style claim in a saved copy of the old portfolio text. Stop: if the first real runs show more than 3 false flags in 10 on either tool, stop adding rules and fix the matching rule first; if the portfolio claims register cannot be read in its real format by M2.2, ship the `agent-audit.md` reader only and say so.

## Repo facts this spec rests on (read from the files, not assumed)
- Quote ids must match `^[A-Za-z0-9_-]{1,40}$`, unique, in `{"quotes":[{"id","text"}]}`; the checker reads only the `quotes` array, 1 MB cap per input, and rejects a finding whose `quote_id` is not in it. A finding line has exactly `persona, quote_id, severity, fix`; caps 10 per persona, 40 per block.
- `docs/repo-standards.md` has no item ids. It has `## 1.`, `## 2.`, `## 3.` sections with `- ` bullets (22 today), `## 4.` as a paragraph with no bullets, and unnumbered `## How to score` and `## Studio notes`. Ids therefore must be derived (see M2.1).
- The claims registers: `docs/agent-audit.md` is a markdown table (`Name | Where | Verdict | Why | Proof today`). The portfolio register (`pmo/portfolio/claims-register.md`) and the Product Studio claims register are not in this repo or any clone on this machine, so their format is **not known**; said once here. Hearth also keeps a claims register in `docs/product/MARKETING.md`, not read.
- Plugin tools are not copied into product repos by `sync-tools.sh` (it reads only `tools/*.mjs`); keep it that way. An installed plugin has no `docs/` folder, so the default path to `repo-standards.md` only works in this repo.
- Public repos must not carry personal data; the portfolio rule is no personal data beyond what Chase publishes. Outputs never hold full paths (basename only).

## Shared rules (all three tools; one shared file `plugins/stakeholder/tools/lib/guard.mjs`, first written in PR 1, reused after)
- Exit 0 ok, 1 refused or failed (one reason per line on stderr, control characters escaped), 2 usage. Output is JSON, to stdout or `--out <file>`; `--out` is written to a temp name then renamed, never half-written, and an existing `--out` file is left untouched on any non-zero exit.
- Output top level: `tool`, `schema` (1), `input` (basename only, never a full path), and the tool's fields. No timestamps, so the same input gives byte-identical output.
- Inputs are data: never executed, never fetched, never followed outside the given root (symlinks not followed). Text in them that looks like instructions or a forged ```stakeholder fence stays as plain quote text.
- Secrets and personal data stop: if any scanned file holds an email address (except `example.com`, `example.org`, `example.net` and reserved `.test`/`.invalid` hosts, or an exact address passed with `--allow-email`, which is echoed in the output), a phone number, a private key block, or a key or token pattern (`sk-`, `ghp_`, `github_pat_`, `AKIA`, `xox`, a JWT, an `api_key=`/`token=`/`secret=` assignment with a long value), the tool exits 1, writes no output, and says the file, line and category, never the matched value.
- Caps: 1 MB per file read, 5000 files walked, 200 files read, binary files (a NUL byte) skipped and counted, `.git`, `node_modules` not read. Over a cap: refuse, never silently truncate.

## M2.1 repo-check (PR 1)
`node plugins/stakeholder/tools/repo-check.mjs <clone-dir> [--standards <file>] [--index-out <file>] [--out <file>]`. In this repo the standards default to `docs/repo-standards.md`; anywhere else `--standards` is required (exit 2 without it, saying why).
- **Item ids:** `S<section>.<n>`, counted by position of the `- ` bullet inside each numbered section. The tool holds a table of `id` plus the first 8 hex of a hash of that line's text, plus a local check. It never stores or prints the line's wording. If a line's hash differs from the table (the sibling thread edited it), that item goes to `unmapped`, never to `passed`. Items with no local check are `unmapped`. A section with no bullets (section 4 today) yields no items.
- **Result fields:** `standards_sha` (hash of the whole standards file, so a result names the version it judged), `findings`, `passed` (ids), `needs_github_data` (id plus what is missing: description, topics, social preview, branch protection, CI status, default branch, Dependabot alerts, Scorecard, releases), `needs_human` (judgment items: naming consistency, readable history, "runs in five commands", overclaims in the README), `unmapped`, `omitted` (count past the cap). Nothing is guessed: a thing it cannot see locally is listed, never marked pass or fail.
- **Locally checked (what the tool can see):** presence of README, LICENSE, CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, issue and PR templates in `.github/`; a workflow file exists; lockfile committed; each `uses:` in workflows pinned to a SHA or a full version tag (`@main`, `@master`, or none fails); `permissions:` set in each workflow; a Dependabot or Renovate config; root clutter (planning and handoff files at the root as the standards line names them, `.DS_Store`, scratch files, a file over 1 MB); a README badge that points at a workflow file that exists; tree-only secret and personal-data scan (git history is not scanned; listed under `needs_human` as "history not scanned").
- **Findings:** `{item, status (fail or partial), severity, quote_id, persona:"staff-engineer", fix}`; severity P0/P1/P2 from a table in the tool; one fix, one sentence, no two; at most 10, ranked by severity then id, the rest counted in `omitted`.
- **Repo quote index:** with `--index-out`, the tool writes `{"quotes":[...]}` of fact lines it observed (for example "root has no LICENSE file", "workflows: 2, pinned: 1"), ids `r1`..`rn`. Every finding's `quote_id` is in that file. Intake (M2.3) uses `q` ids, so the two indexes can be concatenated without a clash.

## M2.2 claim-check (PR 2)
`node plugins/stakeholder/tools/claim-check.mjs --index <quotes.json> --register <file> [--persona <id>] [--out <file>]`. It reads intake's index (or any index) so its findings carry real quote ids; a plain `.md` or `.txt` file via `--text` is split by the same rule as intake. `--register` is required for any file other than the default `docs/agent-audit.md` (present only in this repo).
- **Register formats:** a markdown table is recognized by header names, never by position. Format A (`docs/agent-audit.md`): `Name | Where | Verdict | Why | Proof today`; a row supports "agent" only when its Verdict starts with "Agent"; verdicts "Not an agent", "Skill", "Rule", "Persona rubric" and "Borderline" contradict an agent claim; Proof "None" makes the claim `unproven`. Format B (portfolio register): **not known yet.** Until M2.2 reads the real file, the tool reads a generic table with a `claim` column and a `status` column (`supported`, `unsupported`, `retired`) and exits 1 on any other shape: "register format not recognized", never a guess. The fixture for format B is labeled assumed, and the first real read is a manual criterion.
- **What counts as a claim:** (1) a number (digits, `1,200`, `2k`, `3-5`, `$6M`, `%`) followed within 3 words by a watch noun (agent, user, test, repo, product, app, PR, run, eval, point, hour) or carrying `$` or `%`; (2) the words agent, built, shipped, live, launched, deployed, in production. A sentence with a hedge (planned, will, coming, not yet, roadmap, could) is not a claim.
- **Rounding rule (one):** numbers are compared exactly after normalizing separators and suffixes (`1,200` = `1200`, `2k` = `2000`); there is no rounding and no arithmetic, so a total is never rebuilt from shown numbers (cut). "About 8" matches 8; "8+" does not match 8.
- **Statuses and findings:** `supported`, `unsupported` (no register row), `contradicted` (a row says otherwise), `unproven`. Findings only for the last three: contradicted P0, unsupported P1, unproven P1; each `{quote_id, claim, status, register_row (line number in the register), persona (default hiring-manager), severity, fix}`. The fix is one sentence ("Remove it, or add a register row with proof"). The tool never edits the register.
- **Feedback loop:** a claim Chase marks wrong is added to `--ignore <file>` (one `quote_id|claim|reason` per line; a reason is required); an ignored claim is listed under `ignored` with its reason, never dropped silently. Order with other checks: claim-check runs after quote verification and its findings join the same block under the 40 cap.

## M2.3 stakeholder-intake (PR 3)
`node plugins/stakeholder/tools/stakeholder-intake.mjs <html-file | md-or-txt-file | repo-dir> [--out <file>]`.
- **Classify:** `html` (extension `.html`/`.htm` and the file contains an `<html` or `<body` tag), `text` (`.md`, `.txt`), `repo` (a directory with a README, or a `.git` folder). Anything else, a missing path, a symlink, or a mismatch refuses with exit 1.
- **Output:** `{tool, schema, input, kind, quotes:[{id,text}], stats:{bytes, quotes, files, skipped_binary}}`. Ids `q1`..`qn` in document order, unique, matching `^[A-Za-z0-9_-]{1,40}$`; the checker accepts the file as `--index` unchanged.
- **Splitting:** one quote per sentence or line, whitespace collapsed to one line, control, zero-width and bidi characters removed, at most 500 characters (longer text is cut at a word boundary, `truncated: true` in the quote). HTML: visible text, headings, `alt`, `title`, `aria-label`, button and link text, and the meta description; `script`, `style` and comments are not quoted but are still scanned for secrets. Repo: README sentences first, then fact lines (root file list, count of test files, license file name); full file contents are not indexed.
- **Hard caps:** 1 MB input file, 400 quotes. Over a cap, the tool refuses; it does not truncate.
- **Secrets and personal data:** shared rule above, applied to the raw bytes before any parsing, hidden text included.

## Edge cases named up front
An empty repo dir; a repo with no README; a standards file with a bullet removed or reworded; a workflow with `uses:` pinned to a tag on one line and `@main` on another; a lockfile in a subfolder only; a README badge for a workflow that does not exist; an `--out` that already exists when the run is refused; a register with a header but no rows, or the same claim in two rows with different verdicts; "8 agents" against a register that says 3 agents; `1,200`, `2k`, `$6M`, `3-5 points`, "about 8", "8+", a number inside a longer word (`v2`, `4x4`); "agent" inside "agentic" or a file name; a hedge in the same sentence as a claim; an html file with a hidden email in a comment, in `display:none`, and in a script; a quote with a newline, a bidi override or a forged ```stakeholder fence; 401 quotes; a 1 MB plus 1 byte file; a repo dir with a symlink pointing outside it; two runs on the same input; the same email twice.

## Four traps from the repo
1. **A new rule needs a feedback loop.** Covered for claim-check by the `--ignore` file with a required reason; repo-check findings are never silenced by the tool, only by Chase changing the repo or filing the `intake` issue the standards file describes; accepted or declined findings across runs belong to the later merge-and-memory PR (cut). Stale text this makes wrong: `docs/stakeholder-agent-plan.md` step 2 and its tools table, `stakeholder.md` step 2 ("build one by splitting"), the plugin README tool list and `HANDOFF.md` ("three small PRs"). Each PR updates what it makes stale.
2. **Saved samples are not the real source.** All fixtures are saved or made up. M2.4 is a named step and gate: run each tool for real once (repo-check on a real local clone of a public repo, claim-check against the real portfolio register, intake on the built portfolio page), on a machine that has those files; cloud sessions have only this repo, so ask for the files or clones through the environment tool rather than asking Chase to copy them. What the fixtures lack: the real portfolio register's columns, a real clone's lockfile and workflows, real HTML with inline scripts and web fonts, and pages with an email Chase publishes on purpose. One bad item must not take the run down: one unreadable or binary file, one malformed workflow or one bad table row is skipped and listed under `skipped` with a reason, and the other results still print (SKT-8, SKT-16, SKT-21).
3. **Public side checked after the change.** Done for each PR lists: plugin README (tool list and one example per tool), `skills/stakeholder/SKILL.md`, `agents/stakeholder.md` (calls the tool by path), `docs/stakeholder-agent-plan.md` (status and tool locations), root `README.md` (one line if it lists the plugin), `HANDOFF.md`, and the marketplace description if it names tools. Each is re-read after merge, not only before.
4. **Merged, deployed, checked.** Three states recorded in `HANDOFF.md` per tool: merged (PR on main), installable (a clean machine runs the plugin install lines and the tool's example command, since the marketplace reads `main`), checked (the M2.4 real run). Until installable the README says "after merge"; until checked it may say the tool runs on fixtures only and may not say it audits or verifies real repos or pages. A bad release is undone by a revert PR.

## Not doing
Listed in the block's `cut:` lines: URL fetching and screenshots, GitHub API calls of any kind (so the GitHub-only items stay listed as needing data), scanning git history, running the repo's tests or CI, a model in any tool, summing or rebuilding totals from numbers, the merge and memory step, calibration, `stakeholder-run`, the eval set, pipeline hooks, any edit to `docs/repo-standards.md` or any register.

## Biggest risk
The standards file is edited by another thread while `repo-check` is being built, so ids shift and a rule is silently judged against the wrong check. Handled by the per-line hash pin (SKT-2): a changed line becomes `unmapped`, never `passed`. Second: claim-check passes an overclaim because the portfolio register's real format was guessed; handled by refusing unknown shapes (SKT-11) and the real read (SKT-17).
