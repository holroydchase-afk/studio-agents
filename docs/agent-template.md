# Studio agent template

The checklist every studio agent is held to (Chase, Nov 22: "this is a good template for our agents"). The first eight points come from a build-an-AI-agent course outline, and points 9 and 10 are Chase's additions; where a point assumes a hosted service we say what the studio equivalent is. Status for `ux-reviewer`, the agent being raised first. Other agents start from the same list. See also [ux-agent-bar.md](ux-agent-bar.md) (autonomy tiers, governance, cost).

| # | Template point | ux-reviewer today | Gap and plan |
|---|---|---|---|
| 1 | Reasoning | **Partial.** A written method (checks, then rules, then critic) running on Claude Code's agent loop. We don't own the loop. | Fine to rely on the harness; the gap is that the method has no "stop and escalate" step yet (bar, section 3). |
| 2 | Tools that act | **Mostly.** `ux-shots`, `ux-rules`, `ux-flows` capture; `check-findings` and `check-ux-run` validate; `ux-issues` plans issues (PR in flight). | Filing issues through GitHub and the recheck step are the next two PRs. |
| 3 | Memory and multi-turn context | **Not yet.** Each review is stateless; it writes a run log but never reads the last one. | Before reviewing, read the product's last `uxrun` log and its open `[UX-R*]` issues, so it knows what it already flagged and what was fixed. File-based, no database. |
| 4 | Grounding (RAG or external data) | **Partial.** Reads the studio `design-rules.md` and the product's `docs/design/` tokens. | Add a small curated rules corpus (Apple HIG, WCAG 2.2, Material) as files it searches, with source and as-of date per rule. The HIG page renders client-side and could not be read here, so Chase pastes the text. |
| 5 | A web UI to talk to the agent | **Not yet.** | A read-only page of runs, scores and open findings (a published artifact fed by the run logs), before any chat UI. |
| 6 | Guardrails, validation, fail-safes | **Partial, strong.** No Edit tool, remote targets refused unless a demo, tier gating, output validators, leak scan, review never merges or deploys. | Enforce the per-run cost cap and stop-and-escalate; add a kill switch (a `docs/design/ux-agent.off` file halts it). |
| 7 | Logging and monitoring | **Partial.** `uxrun` log per review with tokens and cost; evals. | Aggregate: score over time, accepted-finding rate, cost per run, one table across agents. |
| 8 | Deploy (FastAPI, production architecture) | **Not applicable as written, and a decision.** Studio agents run inside Claude Code and CI, not as a hosted API. | Studio equivalent: a scheduled GitHub Actions run that captures flows, files issues and rechecks, using the repo's secrets. A FastAPI service only if Chase wants an agent others can call; that is a hosting cost and a privacy decision, so it needs his call. |
| 9 | Context architecture | **Not yet.** The whole 21 KB `ux-reviewer.md` plus the preloaded skill loads on every run (roughly 6,000 tokens), whatever the screen. Nothing is budgeted, summarized or fetched on demand. | Write the order and budget down: (1) always: job, tier, output contract (small); (2) per run: the product's tokens and last run log; (3) on demand: only the rules for this screen type (`design-rules.md` already tags rules by screen type); (4) never inline: screenshots go in as files, one flow at a time. Set a token budget per run beside the cost cap and log tokens used. |
| 10 | Semantic search | **Not yet.** Rules are read whole; past findings are not searched. | Retrieve, don't read: rules, HIG notes, past findings and eval misses, pulled per screen. Start with structured lookup (rule ids tagged by screen type, plus keyword search over the run logs), which is enough for a few hundred items and adds no vendor. Add embeddings only when the corpus outgrows that; it is a new dependency and an architect call, and product screenshots or private findings must not go to a hosted embedding service without privacy-security signing off. Same index powers memory (point 3) and issue dedup: exact `[UX-R1]` ids today, and "same problem under a new id" by similarity later. |

## How the other agents stand
- **qa-tdd, story-keeper:** have 2 (tools), 6 (validators on their output) and part of 7 (evals); lack 3, 4, 5, 8.
- **privacy-security, architect, orchestrator, staff-pm, engineer, release-captain:** mostly points 1 and 2 only. Each needs an output contract with a validator (point 6) before it is raised.
- **positioning:** has none of 2 to 8; the next demotion candidate (see [agent-audit.md](agent-audit.md)).

## Order of work for ux-reviewer
Principle (Chase, Nov 22, from a post on building agents): production agents are mostly a good prompt, a few reliable tools, clear guardrails, structured outputs, human approval where needed, and lots of testing. No agent frameworks (LangChain, CrewAI and the like): the Claude Code agent loop plus our own validators is the stack. Reliability before reach.
1. File issues (merged) and recheck (in flight): the loop Chase asked for.
2. **Reliability**, in this order: structured JSON output for findings (the run log already is the contract; add a `--json` findings file), tool error handling and retries (`ux-flows` fails one flow without losing the rest, retries once), permissions (a written list of what the agent may touch, enforced by the tool list and the demo-only rule), state persistence between runs (read the last run log and open `[UX-R*]` issues first; template points 3 and 9).
3. **A static showcase page** (portfolio-hosted, no backend): before and after shots, the issues the agent filed, its eval score, and one sample run log. This is what a hiring manager sees, so it comes as soon as the loop has one real run on a product. It is a site change: preview it for Chase before it goes live.
4. The scheduled run (8): a CI workflow that does capture, issues and recheck, with the kill switch and cost cap (6).
5. Grounding corpus with structured retrieval (4 and 10); embeddings only if the corpus outgrows keyword search.
6. Aggregate monitoring (7) and promotion to Supervised under the bar's criteria.
7. Last: a live run viewer with a backend (5) and any hosted API such as FastAPI (8), only if a demo needs them; the static showcase page covers most of the need.

## Considered and not adopted: Claude Managed Agents (Nov 22)
Chase decided against building on Anthropic's hosted Managed Agents (paid API usage, beta, not eligible for zero data retention). Kept as reference only, for the ideas worth borrowing: keep credentials out of whatever runs generated code, keep the session log outside the context window so a crashed run can resume from it, and treat the sandbox as cattle, not a pet. Our run logs, validators and planners already follow the same shape. The deploy target stays a CI workflow (point 8 above).
